Quick Start

  1. Attach a TriggerCollider2D or TriggerCollider component to your GameObject.
  2. Click + on any UnityEvent you wish to use.
  3. Drag the CommonUseCaseFunctions asset into the object box. It can be found at:
    Assets > Resources > CommonUseCaseFunctions.asset

You can also use your own scripts — drag in any GameObject that has the functions you want to call.

  1. Select your desired function and you're good to go.

Dependencies

  • Tested and approved for Unity Editor 6000.2.8f1 and above.
  • The Demo scene requires Cinemachine 3.1.5 or above. The core package itself does not depend on Cinemachine.

Common Use Case Functions

The included CommonUseCaseFunctions scriptable object provides a handful of ready-to-use functions for the most common trigger collider scenarios, so you can start implementing and testing without writing any code. Replace them with more tailored versions whenever you're ready.

  • LoadSceneAsync(string sceneName)
  • DestroyObjectCollidedWith(Collider2D collision)
  • DestroyObjectCollidedWith(Collider collision)
  • LogCollision2D(Collider2D collision)
  • LogCollision(Collider collision)

2D and 3D variants of each function only appear when used with their corresponding component. For example, LogCollision(Collider) will not appear as an option on a TriggerCollider2D.

Complex Common Use Case Functions

A dynamic function can only receive what the UnityEvent itself provides — (Collider(2D) collision, GameObject caller) — and a static (inspector) function is limited to 0–1 manually entered values. Some use cases need more configuration than that. For these, CommonUseCaseFunctions uses a companion component to carry the extra data instead of trying to pass it through the UnityEvent itself.

The pattern is:

  1. Add the matching info component to the same GameObject as your TriggerCollider/TriggerCollider2D (the "caller").
  2. Fill in the fields on that component in the inspector.
  3. Assign the complex function to the UnityEvent as usual. At runtime it reads the extra data straight off the info component via caller.TryGetComponent(...).

If the required info component is missing from the caller, the function logs an error and does nothing — it will not throw an exception or stop other functions in the UnityEvent from running.

Example: Instantiate

Instantiate(Collider(2D) collision, GameObject caller) spawns an object when a trigger fires, but it needs three additional pieces of information that a UnityEvent can't supply on its own: which object to spawn, where to spawn it, and how that location should be interpreted. This extra data lives on an InstantiationInfo component:

Field Purpose
Object To Instantiate The prefab or GameObject to spawn.
Location Type How to determine the spawn position — Transform, Vector3, or Collision (the position of the collider that triggered the event).
Transform / Vector3 The transform or coordinates to use, depending on the selected Location Type.

To use it:

  1. Add an InstantiationInfo component to the same GameObject as your TriggerCollider(2D).
  2. Set Object To Instantiate to the prefab you want spawned.
  3. Choose a Location Type and fill in the matching location field.
  4. On the UnityEvent, drag in the CommonUseCaseFunctions asset and select Instantiate.

This same approach — pairing a complex function with a dedicated info component on the caller — is the general strategy for any use case that needs more data than a UnityEvent can carry on its own.

Understanding Trigger Collider Behaviour

TriggerCollider and TriggerCollider2D are identical in functionality and flexibility. The only difference is which physics callbacks they listen to (OnTriggerEnter vs OnTriggerEnter2D, etc.) and whether they rely on Collider or Collider2D.

Both scripts require a Collider (or Collider2D) on the same GameObject. If one is not already present, a BoxCollider (or BoxCollider2D) is added automatically and marked as a trigger.

The default collider type can be changed in Edit > Project Settings > Simple Trigger Colliders.

If the last remaining Collider (or Collider2D) is removed from the object, a new one will be added automatically on the next OnValidate() call (edit mode only). This prevents the script from entering a broken state, since it requires a collider component to function.

Understanding the Unity Events

Each UnityEvent<Collider(2D), GameObject> in the inspector corresponds to one of the three trigger callbacks:

  • OnTriggerEnter(2D)
  • OnTriggerStay(2D)
  • OnTriggerExit(2D)

There are two ways to pass data into functions called by these events:

  1. Static (inspector) — Write the values directly in the inspector.
  2. Dynamic (automatic) — Let the data be passed in automatically through the OnTrigger calls.

Option 1 is straightforward: assign an object, choose a function, and fill in the values.

For option 1, the function must be public, return void, and accept 0–1 parameters in order to appear in the inspector.

For option 2, the function must accept exactly two parameters: (Collider(2D) collision, GameObject caller).

You can still subscribe to a trigger event through code even if your function does not match that signature — you simply won't receive the collision data automatically.

Event Execution Order

The order in which functions listed within a single UnityEvent are called is not guaranteed, and should not be relied on. Consider this inspector setup:

It might appear that the object will, in order:

  1. Play a sound named "pickupCoin"
  2. Play a particle effect
  3. Log the collision
  4. Deactivate itself

However, during testing the observed order was:

  1. Log the collision
  2. Deactivate the object

The sound and particle effect calls were ignored because those components live on the same object. Once the object was deactivated, those functions had no effect.

Every function in a UnityEvent is still called even if the invoking object becomes inactive mid-event. Functions that target components on that same object simply have no effect once it is inactive. See Unity's docs on GameObject.SetActive for more detail.

Solutions

Option A — Move components off the deactivated object

Place the sound and particle components on a separate, always-active GameObject. All four functions will then run as expected.

Option B — Use OnTriggerStay for the deactivation call

The three trigger events do have a guaranteed relative order:

  1. OnTriggerEnter
  2. OnTriggerStay
  3. OnTriggerExit

Moving SetActive(false) into the OnTriggerStay event ensures all OnTriggerEnter functions run first.

Option C — Write custom functions

Implement your own functions so you have direct control over execution order. This takes more effort, but is the recommended approach once you move past initial prototyping — it lets you add error handling and conditional logic to build more robust behaviour.

Common Use Case Functions — How They Work

A scriptable object is used here to work around the UnityEvent limitation that functions must belong to an object reference — not a standalone script.

You can also call these functions directly from code. All functions are static, so they are accessible via CommonUseCaseFunctions.[FunctionName] without needing an instance reference.
